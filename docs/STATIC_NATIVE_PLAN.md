## 1. Decisions and objective

Build a strong **native, flattening-based, IR-only** configuration. Do not use
virtualization in this workstream. Preserve the existing optimized-input build
order: `source -> clang -O2 -> obfuscation -> code generation -> link`.

The objective is to increase the program-specific reasoning and engineering
needed to recover relevant computation, and decrease the reuse of successful
recovery scripts across sites, seeds, and programs. Ghidra/PyGhidra, angr,
bit-vector/SMT solvers, taint analysis, slicing, and custom scripts are attacker
capabilities to evaluate against, not tools to ban to manufacture success.

Flattening, MBA, bogus flow, and increased size are useful ingredients. They are
not automatic evidence of resistance. Compare alternatives at similar costs.
No claim is made that this configuration can make generic software impossible
to reverse engineer.

### Initial implementation scope: F1, F2, F3

The requested "#1, #2, #3" refer to the first three features in the immediately
preceding ranked backlog:

| ID | First implementation features |
|---|---|
| F1 | Normalization-resistant, seeded template diversity. |
| F2 | Constant and data coverage, including values generated by other passes. |
| F3 | Decoder, constructor, initialization, and generated-helper hardening. |

Use existing native passes as the substrate; do not reimplement the entire
flattening/dataflow/call-obfuscation stack as part of these three features.

The newer ideas are explicitly included in the **follow-on IR roadmap** in
section 8: persistent relational encodings, invariant-dependent operations,
and native multi-output fusion are R1-R3. They are not already implemented by
turning on MBA, `sdiff`, or `fmerge`, and do not require a VM. They remain part of
the main IR plan rather than being moved into the MC/post-link parking lot.

### Exclusions

- No VM, bytecode engine, or handler/interpreter development.
- No new MachineFunction, instruction-selector, assembler, or MC transforms.
- No LIEF/post-link mutation or custom pointer patching in this phase.
- No injected assembly/junk-byte gadgets, including ones currently emitted by
  IR passes. Normal compiler lowering and link-time symbol stripping remain.
- No debugger, environment, hardware, timing, licensing, or network checks;
  no runtime gating on those conditions.
- No executable-code decryption, self-modifying code, or packer.
- No prompt injection, tokenizer-specific manipulation, or context exhaustion
  as the principal protection mechanism.
- No new floating-point tricks, arbitrary cross-allocation pointer arithmetic,
  or dependence on undefined behavior.

Future machine/post-link ideas and their entry criteria live separately in
[FUTURE_MACHINE_BINARY_IDEAS.md](FUTURE_MACHINE_BINARY_IDEAS.md).

### Workspace boundaries

- Obfuscator implementation and these documents: this `sre-obf` checkout.
- Fast C challenge and agent loop: the separate `obfuscation-harness` directory.
- Treat `xollvm-work` and its existing wrapper/profiles as reference material;
  do not modify that existing project for this workstream.
- Plan a new harness-local compiler adapter or explicitly versioned packaging
  of the wrapper behavior. Point it at this fork's pinned toolchain/plugin.
  Record any code reuse and version; do not silently reuse the old `max` profile.

## 2. Threat model and evaluation contract

The target contains only ordinary software computation and data. Its behavior
must be correct independent of debugger presence, machine identity, address
layout, or other environmental conditions. Existing address-derived opaque
slots are not environmental checks, but their addresses are not secrets:
recovery tests must permit symbolic addresses and canonicalized address bases.
New state should preferentially derive from program values, build constants,
and initialized per-activation storage.

Before claiming solver/tool resistance, revise and version the harness contract:

- Prohibit native execution of the supplied target or extracted machine code,
  debugger execution, and concrete instruction-emulator queries used as target
  input/output oracles.
- Allow disassembly, lifting, static symbolic propagation, solver queries over
  lifted semantics, static taint/slicing, and scripts implementing recovered
  algorithms. Solver internals evaluating expressions are not a target oracle.
- Classify tool usage by operation, not by package name: angr supports multiple
  modes; PyGhidra is also an automation interface to Ghidra.
- Keep trusted correctness execution separate from attacker analysis.
- Keep target source, answers, instance-generation seeds, maps, and previous
  runs private. Obfuscation seeds are not assumed to be cryptographic secrets.

New standalone-harness bundles use the named `static-recovery-v2` protocol,
allowing static symbolic interpretation. Historical v1 bundles prohibited it;
do not silently mix results across these contracts.

The current runner is not a security sandbox. A launcher must isolate private
files, expose the allowed tools, record traces, and clean up workloads on
timeout. Instruction-level restrictions require an explicit enforcement/audit
design; `chmod -x`, `noexec`, and a correct answer do not establish compliance.

Use two separately labeled attack modes:

1. Binary-only recovery in a fresh context.
2. Mechanism-aware recovery with a curated obfuscator-source snapshot, excluding
   target fixtures, generator code, private build data, and target descriptions.

## 3. Baseline findings to preserve

| Finding | Design consequence |
|---|---|
| The existing wrapper optimizes source first and omits a second `-O2` at object generation. | Preserve that order; do not "fix" it by moving obfuscation earlier. |
| The fork's optional automatic Clang hook runs at pipeline start. | Use the explicit `opt -passes=obfuscation` path after optimized IR; do not enable that hook accidentally. |
| The old wrapper's `max` profile selects VM first and includes anti-debug behavior. | Introduce a new native-only profile rather than aliasing `max`. |
| `constenc`, MBA/SLE forms, `sdiff`, flattening, `vcall`, `fmerge`, `shield`, and `adec` already exist. | Extend existing implementations and measure their actual output. |
| `strenc` has a stub-hardening path. | Reuse its concepts, but audit coverage of all generated helpers rather than assuming every constructor is included. |
| Encrypted `vcall` tables are initialized by code that references targets directly. | Constructor hardening may raise recovery cost, but IR-only work cannot promise removal of all target/relocation clues. |
| `vm` and `flattening` conflict. | VM is forbidden by the new profile regardless of source annotations or nested helper settings. |
| Reports, hierarchical seeds, and IR budgets already exist. | Extend these instead of creating parallel incompatible mechanisms. |

## 4. Proposed profile: `native-max-ir`

The implemented entry point is `-passes=native-obfuscation -native-level=max`.
The settings below remain the design candidate, not a promise of every pass
running on every function. The tested profile prioritizes flattening before
expression expansion: the original order exhausted its budget before flattening.
"Max" is a bounded high-intensity candidate, not a proven strongest configuration.

### Protected-function candidate

The future profile resolver should produce the equivalent of this annotation
for eligible application functions. It must validate the parsed configuration
and effective pass order before publishing an artifact.

```text
obf:
  constenc(prob=100,maxSites=1000,minAbs=2,encInt=1,encFP=0,wrapMBA=1),
  mba(preset=max,prob=100,maxDepth=3,maxSites=300),
  substitution(loop=2,maxSites=300),
  split(num=6),
  sdiff(prob=100,slots=4,maxSites=200),
  bcf(prob=40,loop=1,maxBlocks=1000),
  flattening(minBlocks=2,maxBlocks=1500,allowIndirect=0,hybrid=1,
    opaqueState=1,fakeTransitions=1,fakeCases=4,perDispatcherDomain=1,
    obfuscateStatePtr=1,opaqueAliasStatePtr=1),
  vcall(prob=100,maxSites=128,indexStrength=3,encryptTable=1,
    mergeVTables=0,decoyMin=2,decoyMax=6),
  shield(maxSites=400,volatile=1,identity=1,dse=1,cfg=1),
  adec(prob=100,strength=3,maxSites=100,asm=0,rdtsc=0,
    indirectBr=1,stackPollution=1,deadCodeDecoys=1,
    callObfuscation=1,aliasConfusion=1,fakeLoop=0,constLaunder=1)
```

- `mba(preset=max)` is an arithmetic-pass preset, **not** `vm(preset=max)`.
  Benchmark `mba(preset=high)` as a cost-matched ablation; do not assume stacked
  slot/SLE/input-zero expressions outperform the leaner implementation.
- Record the SLE pool contents/hash as a compiler input. A build-time pool file
  or build seed is not a target runtime environment check.
- Preserve `flattening -> vcall -> shield -> adec` ordering in the native path.
  Direct-to-indirect call conversion before flattening can make it ineligible.
- `asm=0` and `rdtsc=0` are required but not sufficient policy enforcement:
  reject injected gadget files/inline asm settings and audit generated IR/code.
  Audit generated regions rather than flagging arbitrary byte sequences or
  unrelated runtime-library instructions as obfuscator features.
- `allowIndirect=0` is an initial correctness/eligibility boundary, not a claim
  that indirect dispatch is undesirable. Report unsupported original functions.
- New F1-F3 controls need their own registered options and tests. Do not pretend
  the existing annotation above already implements these extensions.

### Module work and helpers

- Enable existing string encoding with explicit settings, initially
  `strenc(cipher=aes,keysplit=1,minlen=1)` for eligible literals; compare ChaCha
  as an ablation rather than assuming cipher strength determines RE difficulty.
- Enable bounded `fmerge` for eligible application groups, starting with
  `fmerge(chunk=4,opaqueSel=1,launderSel=1,dispatch=switch,thunkAddrTaken=0)`.
  Do not merge constructors/runtime helpers with applications by default.
- Function merging is module-local. The two-TU crackme may have no eligible
  merge group after `-O2`; report this and exercise merging in a separate small
  multi-function fixture. Do not distort the clean challenge just to force it.
- Give generated helpers explicit profiles through F3. Do not recursively apply
  the entire profile to every new helper with no generation or size bound.
- Preserve required external interfaces and address identity. Start with
  internal C functions and fixed-size compiler-owned data; defer new EH,
  vararg, escaping-object, and custom-ABI support.

### Selection, limits, and failures

Protect all eligible challenge-owned functions in the small fixtures. For
larger programs, record explicit coverage/selection limits rather than silently
spending the budget on library templates or selecting only a few large bodies.

Initial existing-driver guardrails to calibrate in M0:

```text
-obf-verify
-obf-deterministic
-obf-ir-budget-multiplier=50
-obf-ir-budget-max=30000
-obf-max-function-insts=3000
```

The multiplier is a guardrail, not a target expansion ratio. Also budget total
module/generated-helper IR, final binary size, process memory, compile time,
and runtime. Per-function budgets alone miss constructor/global-data growth.
Start with a 180-second timeout per transform/codegen invocation for fast-loop
fixtures, and publish any calibrated change as a new configuration revision.

Fail validation when a fixture's required protection was skipped, rolled back,
or silently disabled. Distinguish "no eligible site" from budget failure.
Allow an explicitly labeled unsupported-function fallback for broad programs,
but never call it full native-max coverage. Unsupported/slow configurations
remain failed configurations; they are not successful obfuscation results.

## 5. Build and pass pipeline

Start with x86-64 Linux ELF PIE and a pinned LLVM 22.x revision/toolchain image.
Pin the exact compiler/plugin/runtime-helper hashes in M0. If a different LLVM
version is chosen, record the decision and regenerate all matched controls.
Do not enable LTO/ThinLTO in the first milestone.

```text
source
  -> clang -O2 -> shared optimized IR
  -> select/annotate + assign stable origin IDs
  -> module preparation: bounded fmerge, string/data handling
  -> native flattening
  -> indirect-call transformation
  -> constant/expression/dataflow transformations with F1 diversity
  -> bounded generated-helper hardening and late-data coverage
  -> final shield / IR-only adec / verification
  -> same object-generation settings as the matched clean control
  -> ordinary link (no custom post-link transform)
```

This is a target stage design, not permission to blindly reorder existing
passes. Existing module transforms run outside the function driver. F2/F3 must
integrate with annotation caches, analysis invalidation, and helper creation.
Add an explicit late stage/worklist where needed; repeatedly listing `constenc`
in an annotation is not a reliable second pass because pass lists are deduped.

Use a bounded generation scheme: discover/tag roots, process each helper once
under its assigned profile, and audit the resulting closure. Avoid an infinite
cycle where hardening a decoder generates another unprocessed decoder.
IR verification checks well-formedness; it does not prove semantic equivalence.

### Matched controls

Keep these distinct:

1. Ordinary release `clang -O2` baseline.
2. Shared optimized IR -> no obfuscation -> the same backend/link settings used
   for protected builds.
3. Existing native candidate before F1-F3.
4. Candidate with each feature alone, cumulative combinations, and combined
   minus one feature.

The second control isolates the effect of the wrapper's no-second-`-O2` path
from the obfuscation itself. Code generation still performs lowering and may
simplify transforms; omitting another `-O2` does not freeze instruction shape.

## 6. First implementation feature specifications

### F1: normalization-resistant template diversity

Extend shared opaque/expression infrastructure rather than building independent
RNG/template systems in each pass.

Deliverables:

- A versioned family registry describing supported widths/operations,
  preconditions, memory effects, estimated cost, and private family/site IDs.
- Initial consumers: scalar materialization, MBA/opaque expressions, flattening
  state updates, and eligible index/decoder expressions.
- A small set of genuinely different families first: arithmetic/bitwise forms,
  bounded storage-mediated forms, and different dependency/operation groupings.
  Retain only families that pass correctness and compiled-form evaluation.
- Stable seed namespaces for family selection, coefficients, layout, and
  probability decisions. Generated sites derive IDs from a parent origin and
  role, not transient memory addresses or the order of unrelated RNG calls.
- Measured family diversity at IR, assembly, and normalized decompiler levels.
  Preserve constants, widths, predicates, and signedness in semantic views.
- Explicit limits on recursive rewrites and generated expressions.

Do not impose an arbitrary "no template above 10%" rule on tiny functions. Report
coverage and effective normalized families. All coefficients are recoverable
data, not hidden cryptographic keys. Changing them alone is not structural
diversity.

Acceptance:

- Width/edge-case fixtures preserve defined semantics; unsupported equivalence
  models are not treated as proof.
- Fixed inputs/configuration/seeds reproduce artifacts, with normalized module
  identities and compiler inputs captured.
- A script learned on one family/site is tested unchanged on other families,
  seeds, and programs, then given to an agent for repair.
- Families collapsed by compiler/decompiler normalization are removed from the
  claimed effective diversity or redesigned.

Primary code: `OpaqueUtils.cpp`, `MBAUtils.cpp`, `MBAObfuscation.cpp`,
`ConstantEncryption.cpp`, `Flattening.cpp`, `SemanticDiffusion.cpp`, and reports.

### F2: constant and data coverage

Cover representations that scalar operand replacement misses. Begin with
private/internal fixed-size byte and integer arrays whose uses can all be
rewritten safely. Preserve external/address-sensitive objects unchanged with
an explicit reason until a correct transformation exists.

Deliverables:

- Inventory original and generated scalar constants, arrays, selector data,
  key material, and decoding sites using private origin mappings.
- Encode eligible data and rewrite reads, including repeated and indexed use.
  Select per-site/per-object representations through F1.
- Audit cloned/inlined copies and constants introduced by flattening, `vcall`,
  helper creation, and later transformations.
- Add a bounded late constant/data coverage stage. Tag transformed sites to
  avoid indefinitely encoding the encoding constants themselves.
- Report unavoidable literal operands separately: switch cases, intrinsic
  immediates, ABI-required data, and structural operands cannot all be replaced
  arbitrarily. Where structural lowering is necessary, make it explicit work.

Prefer immutable encoded backing with rewritten accesses for the initial
non-escaping data subset. Where decoding requires mutable backing, allocate
valid writable storage and establish initialization-before-use. Do not write
into actual `.rodata`, change pointer identity silently, or introduce racy lazy
initialization. First-use and constructor ordering are correctness concerns,
not environmental defenses.

Acceptance:

- Scalar and array fixtures cover i8/i16/i32/i64, boundaries, multiple users,
  multiple TUs, signed loads/extensions, and constructor-time reads.
- Compare real computation outputs, not only accept/reject behavior.
- Raw constant scans identify accidental copies but are only a smoke test;
  account for incidental equal-valued constants and alternate representations.
- Recovery attempts include static propagation, constructor analysis, and bulk
  decoding. Finding one decoder must be tested against every protected object.
- Residual call-target references/relocations remain documented limitations of
  this IR-only phase, not hidden successes of pointer encryption.

Primary code: `ConstantEncryption.cpp`, `StringEncryption.cpp`,
`VirtualCall.cpp`, module orchestration, plus a new bounded data-encoding stage
if scalar/string passes cannot own it cleanly.

### F3: decoder and initialization hardening

Make generated support code a first-class part of the protection surface.
Obfuscating application bodies while leaving an obvious global decoding recipe
does not satisfy this feature.

Deliverables:

- A helper/initializer dependency inventory: who creates a helper, what data it
  decodes, who calls it, and which state must exist before it runs.
- Explicit generated-function registration, origin/protection role, profile,
  generation bound, and coverage status. Do not rely only on name prefixes.
- Reuse and extend `strenc` stub-hardening support to eligible decoding, key
  materialization, selector initialization, and `vcall` constructor paths.
- Diversify helper bodies and conversion boundaries using F1; protect their
  scalar/data operands using F2.
- Test bounded local inlining/outlining or merging only where ABI, lifetime,
  constructor ordering, and data dependencies remain valid.
- Correct internal linkage for compiler-owned helpers, while preserving real
  imports/exports. Keep helper maps out of the public artifact.

Do not make every helper recursively decode another helper's prerequisites.
Constructor dependency graphs must remain valid under startup order and
reentrancy. Avoid creating new allocation failures, I/O, exceptions, or runtime
side effects unrelated to the source program.

Acceptance:

- Every relevant generated root/helper is either covered or explicitly
  exempted; helpers created late cannot disappear from the report.
- Startup, repeated calls, multiple TUs, and supported recursion/reentrancy
  cases preserve behavior.
- Give a static extractor the correct decoder entry address as an additional
  diagnostic: this separates hidden discovery from hard semantic recovery.
- Measure whether one recovered helper still unlocks all objects/sites and
  how much work is required to adapt that attack across variants.

Primary code: `StringEncryption.cpp`, `VirtualCall.cpp`, `FunctionMerging.cpp`,
module/function orchestration, annotation caches, pass ordering, and reporting.

## 7. Evaluation and implementation milestones

### Evaluation fixtures

- Existing simple C crackme: fast binary solve/fail loop; independently measure
  its clean agent solve cost before treating obfuscated failures as protection.
- Integer kernels exposing full outputs: do not let random all-reject password
  tests conceal a broken transform.
- Small array/constructor/multiple-TU fixtures for F2/F3.
- A small same-module multi-function fixture for merging and native dispatch.
- Later, separate held-out RevDeflate/RevGame-style programs for transfer.
  Do not make the larger corpus the inner-loop default.

### Measurement layers

Capture shared optimized IR, per-stage transformed IR, assembly, object
relocations, linked ELF, Ghidra decompilation/intermediate representations, and
at least one independent static recovery view when available. MIR snapshots
are optional diagnostics; inspecting them does not authorize machine passes.

Use three distinct outcomes: compiler survival, analysis/normalization
survival, and actual semantic/answer recovery. Pseudocode size and decompiler
crashes are diagnostics. A broken tool model is not automatically resistance.

Repair the fork's benchmark assumptions when reusing it:

- Its runner starts from `-O0`; add the matched after-`-O2` path.
- Its call-target score counts indirect calls; add real target-set recovery.
- Its decompiler score rewards growth/crashes; retain diagnostics but separate
  answer/semantic recovery.
- Its MBA lifter replaces unsupported operations with unconstrained values;
  classify incomplete modeling explicitly instead of treating it as success.
- Run attacks in killable process groups/resource containers; an abandoned
  timeout thread must not contaminate later trials.

For each successful extractor, retain unmodified-reuse, agent-repair, and
cross-program-transfer tests. Use fresh contexts, fixed tool/model versions,
fixed solve budgets, independent held-out seeds, and separate development vs
held-out attack portfolios. A first small seed sweep is a screening exercise,
not statistical evidence of general-purpose resistance.

Record correct recovery, wrong answer, budget exhaustion, unsupported model,
and infrastructure failure separately. Record token/cost usage only when the
adapter supplies it; wall time is not a substitute. End-to-end scoring remains
the exact private answer, not a decompiler appearance score.

### Milestones and completion gates

| Milestone | Work | Completion gate |
|---|---|---|
| M0: baseline and protocol | Pin tools; add planned native profile/resolver and harness-local adapter; version static-analysis contract; establish controls, coverage, fixtures, costs, and repeatable extractors. | Required flattening is demonstrated on eligible fixtures; VM/asm/timing obfuscation absent; clean correctness and matched builds pass. |
| M1: F1 | Shared family/seed infrastructure and initial consumers. | Verified semantics, deterministic artifacts, measured post-normalization diversity, and extraction-reuse results. |
| M2: F2 | Eligible scalar/array coverage and bounded late coverage. | Correct full-output/array/init fixtures; all intended objects accounted for; no unreported plaintext copies on fixtures; recovery results retained. |
| M3: F3 | Generated-helper registry/worklist and decoder/init coverage. | No unreported helper gaps; no initialization/ABI regressions; informed-entry and bulk-decoder recovery tests complete. |
| M4: integrated native candidate | Combine F1-F3, run leave-one-feature-out and cost-matched comparisons, then held-out agent/program trials. | Correctness and resource gates pass; report actual recovery/repair costs, including regressions. Promote only demonstrated improvements. |
| M5+: follow-on IR | Prototype R1 then R3, followed by R2/R4 as justified. | Each feature gets its own correctness, ablation, and recovery gates before default enablement. |

Do not silently substitute weaker coverage to make a deadline. If a setting
miscompiles, times out, or rolls back a required pass, preserve diagnostics and
revise the candidate explicitly. Completing an implementation milestone is not
the same as demonstrating improved protection.

## 8. Follow-on IR roadmap: the newer ideas

These research extensions stay entirely at IR level. Initial bounded R1,
R2-coupling and R3-outlining infrastructure is implemented as described in the
linked experiment document; the broader research objectives below are not all met.

[v01](NATIVE_V01.md) now implements additional bounded versions of R1–R5,
including cross-TU/native fusion, wide shares, mutable local memory, reachable
witness semantics and static recovery selection. The table remains a research
direction, not a claim of arbitrary-program coverage or tool resistance.

| ID | Idea | Native implementation direction | Gate / principal risk |
|---|---|---|---|
| R1 | Persistent relational value encoding | Jointly encode two/few live integers and implement a restricted operation family without decoding at every use. Carry the representation across native blocks. | Prove transfer functions; test recovery of the joint representation. Local encode/decode wrappers that simplify away do not count. |
| R2 | Invariant-dependent operation semantics | Maintain a relation between data and per-activation state; rewrite operations to be equivalent over reachable states, integrated with native flattening transitions. | Prove entry, transition, and join invariants. Never substitute arbitrary behavior on reachable states or rely on poison. Simple hidden constants may collapse the idea. |
| R3 | Bounded native multi-output fusion | Extract pure integer SSA regions, jointly rewrite/synthesize their real outputs, and lower back to native IR. No bytecode, VM handlers, or interpreter. | Preserve exact input/output semantics and side-effect ordering; cap growth; test region-level simplification and recovery. |
| R4 | Phase-dependent local memory representation | Change representation of fixed-size nonescaping objects at defined block/phase boundaries, coordinated with a private activation context. | Validate bounds, alignment, lifetimes, phase joins, and reentrancy. Avoid a universal easy accessor. |
| R5 | Attack-guided candidate selection | Search a bounded set of verified F1/R1/R3 candidates using cheap static recovery tests and fixed overhead limits. | Hold out programs, tools, and attacks; do not optimize solely against one decompiler version or incomplete lifter. |
| R6 | Proof-erased opaque predicates | Generate small predicates with verified invariant outcomes; retain the proof privately and evaluate static proof/recovery difficulty. | Research only: UNSAT does not imply hard UNSAT, and execution cost may dominate. Defer behind R1-R3. |

Ordinary bit-precise integer semantics are part of all these designs, not a
standalone claim that Python cannot reproduce C. Floating-point/x87/FMA tricks
remain excluded. Carry/condition-flag-specific synthesis belongs to the future
machine document because controlling its emitted implementation is target work.

Architectural preparation during F1-F3 should support these extensions:

- Typed encoding descriptors and explicit conversion boundaries.
- Origin/role IDs that survive grouping and helper generation.
- Per-activation state ownership, not process-global mutable dispatch state.
- Explicit effect summaries and analysis invalidation.
- Bounded region interfaces suitable for equivalence tests and attack fixtures.

Do not implement the full research features merely to build this scaffolding.

## 9. Definition of the first completed delivery

- An implemented, documented, native-only `native-max-ir` profile using this
  fork and the after-`-O2` pipeline, with calibrated settings and no implicit VM
  or assembly-gadget path.
- F1-F3 implemented behind independently controllable, recorded options.
- Coverage includes application code, eligible data, and relevant generated
  support code; exclusions and residual IR-only leaks are explicit.
- Correctness, deterministic-build, compiler/decompiler-survival, and recovery
  tests run against the same shipped artifacts with private ground truth.
- A reproducible result set comparing baseline, existing native configuration,
  individual features, combinations, and leave-one-out variants.
- A report of agent solve/repair/reuse costs and overhead, without treating a
  failed lifter or an unmeasured clean target as evidence of strong protection.
- R1-R6 remain separately tracked IR work; machine/post-link ideas remain
  documented but unimplemented until a measured reason justifies that scope.

This is the roadmap, not an assertion that every acceptance item is complete.
F1-F3, state hardening, and bounded value/region/coupling experiments have
implementations; consult the linked status and audit for exact evidence.
Generalized R1-R6 coverage and agent solve/repair measurements still require work.
